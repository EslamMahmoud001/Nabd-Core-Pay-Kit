# KB-01 — Nabd Core + Pay system guide

**Baseline:** application commit recorded in `qa/SOURCE_BASELINE.md` · **Scope:** Core + Pay only

## 1. Product shape

Nabd is delivered as a dedicated application and PostgreSQL database per customer deployment. Core is the integration and HR-data foundation and is always on. Pay is a module-gated payroll engine and operator UI. Pay reads Core data; module ownership and write boundaries must be respected.

Local defaults are CAP `:4004`, Core `:3002`, Pay `:3003`, and the shipped PostgreSQL compose mapping `:5432`. Runtime overrides can change database credentials/target, so verify the resolved environment rather than copying old tenant values.

Background jobs run in the CAP process through `node-cron` and persisted job/schedule configuration. There is no Redis/BullMQ runtime dependency in the current clone.

## 2. Evidence hierarchy

For any behavior claim, use this order:

1. `CLAUDE.md` and `docs/README.md` in the active clone.
2. The relevant current feature document.
3. Route/page code and role-routing helpers.
4. Service contract, handler, schema, and focused tests.
5. The running app and tenant data.
6. This kit.

Record the clone commit. If documentation and code disagree, call out the discrepancy and treat executable handler/tests as authoritative for the tested build.

## 3. Core

Core owns connection administration, SuccessFactors synchronization, foundation/employee/time data, S/4 G/L-account sync, job schedules, audit/alerts/notifications, Data Browser, module settings, and branding. Current navigation includes the hub and employee, leave, timesheet, balance, foundation, S/4 account, and advance streams.

SuccessFactors connection options include the modes implemented in the active clone, including SOAP Basic and OAuth2 SAML Bearer. Credentials and destination data live outside the kit. A successful connection is not proof that every domain sync completed; verify job status and target row/state separately.

## 4. Pay configuration model

- **Pay Items / Component Studio:** effective-dated item versions, ownership, calculation/cumulation contract, version timeline, supported hard delete. `effectiveTo` is derived from version order where the current PAY-084 contract applies.
- **Parameters, Schemes, Bracket Tables:** effective-dated lanes cannot overlap. Gaps are valid; do not “repair” a deliberate gap without a requirement.
- **Rules and country packs:** provide calculation/catalogue behavior. Confirm activation and effective dates.
- **Calendars/cycles:** define payroll time. Actual execution requires the cutoff cohort to have been frozen. Never assume an open cycle is runnable.
- **Readiness and Preflight:** distinct gates. Report checks as findings with their configured severity and context.
- **Approval policies:** stage roles and segregation-of-duties are policy-driven. Development super-users can mask real persona conflicts, so test with intended personas.
- **G/L, bank, payslip, loans, EoS/leave, retro and off-cycle studios:** each has its own role, state, and data prerequisites.

## 5. Run lifecycle and results

The standard spine is configure → generate/open → readiness → cutoff/freeze → dry run → actual run → approvals → G/L post → close → downstream outputs.

- Dry runs are safe calculation lanes but still create state. Current behavior includes cycle-level audited discard.
- Run Wizard supports manual selection and CSV/XLSX employee-selection import.
- Reruns must replace/reconcile prior work without leaving orphan results; verify counts and totals after rerun.
- Actual runs use the frozen cohort; treat cutoff as a material state transition.
- Close is a permanent lifecycle transition in normal operation. Use only when the target scenario requires it.
- Results route access and sensitive compensation/identity fields have separate authorization rules.

## 6. Outputs

### Bank files

Bank Template Studio stores data-driven template specs. Current layouts include delimited, fixed-width, XLSX and XML. Generation uses eligible actual payroll results, primary bank information, positive net pay, a single currency, and the current lifecycle gates. Full sensitive values are used only in protected storage/generated bytes; preview stays masked/synthetic. See `reference/BANK_TEMPLATES.md`.

### Payslips

Payslip Studio must keep preview and PDF output aligned. Batch generation and SuccessFactors push expose actionable, retryable error state. Reconcile generated counts to the eligible cohort.

### G/L

G/L requires active mappings and a balanced journal. View, configure, post and reverse are separately role-gated. Posting is a financial action; record destination/simulation mode and response.

### Reports and analytics

Filters and source run matter. Analytics/report handlers may use dry-result fallback where implemented. Always state the selected calendar/cycle/pay group and reconcile totals to results. Report scheduling is outside this kit's committed scope.

## 7. Roles, capabilities, and feature release

Customer roles include tenant admin, consultant, payroll admin, payroll manager, approver, HR director and finance director; `tc_ops` serves Core operations. Consultant is primarily a configuration author and does not imply access to live compensation/personal/raw SF data. Finance authority does not imply employee identity access.

Feature release is an additional gate: access requires the normal role and a released feature, unless the caller holds the preproduction-only `preprod_tester` scope. Tenant admin can view the release board and the current handlers define who can change it. The frontend route/nav guard is defense-in-depth; backend authorization is authoritative.

Use `app-pay/src/lib/role-routing.js` for UI bundles and the relevant handler/service contract for actual authorization. Never infer an action permission only because a page is visible.

## 8. Destructive and high-impact operations

Confirm environment and intent before actual run, approve/reject/reroute, post/reverse, close, hard delete, discard, regenerate, external push, or release-toggle changes. Capture before/after identifiers and status. Product-supported deletion varies by state: unused/dry history may be hard-deletable, while committed history is archived or otherwise protected.

## 9. Scope exclusions

Workforce is not part of the current product scope. AI & Compliance, AI-assisted output, and deferred scheduling/setup-wizard roadmap items are not part of the kit. Do not surface them as delivered Core + Pay functionality.
