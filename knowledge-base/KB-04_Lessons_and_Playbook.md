# KB-04 — Core + Pay operating playbook

## 1. Diagnose by layer

When a flow fails, classify it before changing anything:

1. **Environment:** process, port, database/profile, destination, module flag.
2. **Authorization/release:** persona role, action capability, feature release.
3. **Data:** missing or stale Core inputs, wrong pay group/calendar/cycle, absent template/mapping.
4. **Configuration:** inactive/effective-dated item, overlapping lane, scheme/parameter/preflight rule.
5. **Lifecycle:** wrong cycle/run/approval/post/close state or unfrozen cohort.
6. **Product defect:** code behavior contradicts contract/tests after the first five are disproved.

Preserve the first failure payload and identifiers. Random retries destroy useful evidence.

## 2. Effective-dated configuration

For Pay Items, Parameters, Schemes and Bracket Tables, inspect the complete lane and target date. Gaps can be intentional; overlaps are invalid. A value visible today may not be effective for the cycle being tested. Pay Item version end dates may be derived, so do not manually assert dates without checking the current contract.

## 3. Regular payroll

- Confirm calendar/cycle, pay group, employee cohort and configuration effective date.
- Resolve readiness findings by evidence; do not disable hard checks merely to obtain a green screen.
- Cutoff freezes the cohort used by actual execution.
- Dry run first and reconcile employee count, gross, deductions, net, errors and trace.
- If selecting employees via CSV/XLSX, test validation feedback and reconcile the accepted list.
- Before rerun/discard, record run/cycle IDs. Afterward confirm old/orphan results are not counted.
- Actual, approvals, G/L and close are consequential; use intended personas and record each transition.

## 4. Leave/EoS, retro, off-cycle and loans

- Leave/EoS depends on time-account types/balances and scheme configuration. Multiple time types are supported; a missing type should be surfaced as a warning where the current handler specifies it. Verify `working_days_per_month` and other active parameters rather than assuming a divisor.
- Retro begins with a legitimate effective-dated source change and an eligible next cycle. Confirm trigger creation and the recomputed difference.
- Off-cycle needs an eligible item/person/reason and its own lifecycle. Do not hand-insert a result.
- Loans/advances begin with an approved principal/policy input; Nabd must generate the schedule and deductions.

## 5. Outputs

### Bank file

Start from the bank's actual layout specification/sample and the current interpreter source catalogue. Validate structure before activating. Prove eligibility, masked preview, generated bytes, row count, totals, filename, encoding, dates, typed spreadsheet cells and leading-zero preservation. For multi-bank work, validate each template independently and activate on QA only after local success.

### Payslip

Compare studio preview with generated PDF, reconcile batch counts, and inspect any SF push failure message/retry status. Do not conceal failed pushes in a “completed” claim.

### G/L

Check mapping coverage and debit/credit balance before post. Record external destination or simulation mode. Post/reverse requires finance authority or tenant administration according to current handlers.

### Reports/analytics

State filters and source run. Reconcile totals to Results. A blank view is often a filter/pay-group mismatch; a populated dry fallback must be labeled as such when explaining evidence.

## 6. Capture stability

- Explore first, automate second.
- Prefer role-based/text/test-id locators and direct verified routes over brittle coordinate clicks.
- Wait for a meaningful state assertion, not a fixed delay.
- Clear menus/dialogs/tooltips before capture.
- Hash every image and fail on duplicates.
- Keep diagnostics (route, assertion, timestamp) outside the screenshot set.
- Use the target persona; a super-user capture can teach controls the stated role cannot use.

## 7. Anomaly versus configuration gap

An anomaly needs reproducible observed behavior and evidence. First rule out environment, authorization/release, data, configuration, and lifecycle state. If unsupported behavior remains, record it using the anomaly template; never edit the clone to hide it.

## 8. Drift refresh

For a new app clone: record commits, diff the prior baseline, group changes by Core/Pay feature, re-check routes/roles/service contracts/tests, update kit references/KB/skills/commands, then run static and scenario validation. `qa/SOURCE_BASELINE.md` is the ledger.
